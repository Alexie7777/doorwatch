系统架构说明

让 IT 办公室的门可以被看见

门磁传感器 → MQTT → 一个网页。老师在手机上花两秒确认"门开着还是关着"， 不用再跑到办公室门口才发现扑空。

这套东西的核心难点不在"读取开关状态"，而在设备掉线时不能撒谎。 下面这份说明会重点讲清楚这件事是怎么处理的。

整体架构

纵向分四层。现场层把物理门变成 MQTT 消息，服务层把消息变成可信状态， 展示层把状态变成一个不用问人的答案。

图 1 · 四层架构。竖直方向是数据流:物理开合 → MQTT 消息 → 可信状态 → 人类可读的答案。

硬件侧:门磁、隔离与供电

门禁系统里已经有的门磁可以直接复用,不用再买传感器。 但必须解决两件事:电平隔离(否则烧板)和电压转换(12/24V → 3.3V)。

图 2 · 复用门禁门磁的原理图。左半边是门禁的 12/24V 域,右半边是 ESP32 的 3.3V 域, PC817 把两者彻底隔开,门禁系统照常工作,互不干扰。
动手前务必先量三处电压。 ① 门禁电源是 12V 还是 24V? ② 门磁两个端子对控制器 GND 的电压 —— 门关≈0V、门开≈12/24V 说明控制器有上拉,必须加光耦; 两种状态都≈0V 才是纯干接点。 ③ 门禁电源带不带 UPS 后备?带的话最理想,停电时看板跟着门禁一起活。

ESP32 固件逻辑

固件本身不写 C 代码。我们写的是一份 ESPHome 的 YAML 声明,ESPHome 把它编译成固件烧进 ESP32。 下面这份 YAML 不到 130 行,里面没有一行 if/else —— 全部行为都由配置项决定。

启动阶段

上电到进入稳态,一共五步。首次烧录后手机连 IT-Door-Setup 热点配网,就发生在第 2 步。

  1. 上电启动

    ESPHome 运行时起来,初始化 GPIO 与 WiFi 协议栈

  2. 连 WiFi

    连不上就自动开热点 IT-Door-Setup,手机连上配网即可

  3. 连上 Broker

    立刻发 birth_message = online,宣告自己上线

  4. 上报当前状态

    不管门此刻开着还是关着,先把此刻的真实状态发一次(retain)

  5. 进入稳态

    启动 60 秒心跳定时器,此后只做两件事:门变了就报、每分钟证明自己活着

关键分工

这是整套设计里最容易误解的一点。

ESP32 负责
· 如实汇报 "我看到的门是开还是关"
· 定期汇报 "我还活着"
· 不判断自己算不算在线
服务端负责
· 判断这条消息 现在还能不能信
· 决定显示开门 / 关门 / 未知
· 设备瘦一点、少一点逻辑,就少一处出错的地方

所以把 ESP32 换成别的方案(门禁系统推事件、Zigbee 传感器), 服务端的判定逻辑一行都不用改。

图 4 · 固件的三条上报路径。注意 ③:设备死后是 Broker 发的 offline,不是设备自己发的 —— 设备都死了,自然没法发消息。

YAML 配置 → 实际行为对照

YAML 片段干了什么对应上图
pullup: true门磁断开时 GPIO 被内部上拉拉高,不用外挂电阻硬件侧
filters: delayed_on/off: 1000ms门被风吹、被推一把会抖好几秒,滤掉① 去抖
payload_on: "OPEN"状态变化时自动发消息,不用写任何代码① publish
retain: true保留最后状态,服务重启后一订阅就能拿到① publish
birth_message: online连上 Broker 的瞬间宣告自己上线启动 ③
shutdown_message: offline登记遗嘱,设备死后由 Broker 代发离线③ 掉线
interval: 60s定时器,周期性地证明自己还活着② 心跳
captive_portal + ap:连不上 WiFi 时开热点,手机连上配网启动 ②
status_led板载 LED 当状态指示,配网时能确认设备活着辅助
为什么心跳不 retain? state 是"当前是什么状态",值得保留;heartbeat 是"我刚才还活着", 保留一份过期的"活着"没有意义,反而会让服务端误判。新的心跳到了自然覆盖旧的。

数据流:从推门到看板变色

门被推开到手机上变色,中间发生的事。整条链路是推模型,看板不需要问任何东西。

  1. 物理开合

    门扇移动 → 磁力开关触点断开 → 控制器侧检测到门开

  2. ESP32 感知

    GPIO 电平变化 → 经 1 秒去抖过滤(防止风吹、推挤造成的抖动)

  3. 发布状态

    doorwatch/it-office-door/state = "OPEN"
    QoS 1 · retain=true —— 服务器重启后订阅即得最后状态

  4. Broker 转发

    内置 aedes broker 收到并转发给订阅者;同时记录 retain 值

  5. 服务落库 + 广播

    写入 SQLite events 表(仅状态真的变化时才记一条)→ SSE 广播全量状态

  6. 看板重绘

    所有打开的页面通过 SSE 收到新快照 → 重绘卡片颜色。不刷新页面、不轮询。

MQTT 主题契约

主题载荷作用
…/state OPEN / CLOSED 门状态变化,retain
…/status online / offline 遗嘱消息,掉线时由 Broker 代发
…/heartbeat alive 每 60 秒一跳,判断设备是否活着
…/battery 百分比 仅电池版上报,用于低电量提醒

前缀固定为 doorwatch/<deviceId>/。 deviceId 必须与 config/doors.json 完全一致,否则服务会忽略该消息并在日志中报警。

三态判定:整个系统最关键的一段逻辑

看板有三种状态,不是两种。第三种才是这个系统的价值所在 —— 它保证传感器掉线时看板不会撒谎。

图 3 · 有效状态判定链。任何一关不通过,一律降级为 unknown。

朴素做法的问题

传感器挂了之后,门磁会保持最后一次上报的状态。如果直接把这个状态显示出来:

最后一条是 "CLOSED" → 传感器死了整整一周 → 看板每天都显示"已关门"。

用户看到"关门"就更不会来了 —— 系统恰恰在最需要它的时候彻底失效。

本方案的处理

只有确认设备活着(心跳新鲜 + 未报离线)且状态合法,才敢显示开或关。

其余一律显示 unknown,用醒目的琥珀色提示"数据不可信,请联系 IT"。

此时看板拒绝给答案 —— 这比给一个错答案诚实得多,也更有用。

为什么不用 Home Assistant? 如果学校已经在跑 HA,那用它更省事 —— ESPHome 固件本来就发标准 MQTT,HA 能直接发现。 但 HA 本身有学习成本和插件依赖,而这个场景只需要三件事:一个网页、三个状态、一条历史。 所以这里保持零依赖,一条 docker compose up -d 就能跑。

选型前置检查

动手之前先把这几件事查清楚。B 组必须拿万用表实测,不能靠猜 —— 门禁品牌型号不同,内部接法差别很大。查出来不满足的项,直接对照下面的降级路径走, 别买到料了才发现做不成。

适用范围:这一节只对 ESP32 + 干接点门磁那条硬件路线有意义。 本项目当前采用米家门磁 + Home Assistant 路线 —— 不碰门禁锁体、不动线、不借电,下面这些门禁侧实测一项都不用查。 留着是给将来可能改走硬件路线的人当参考。

A · 门体与门禁侧(现场看)

  • 门磁是不是独立端子?有些门禁把门磁和出门按钮并在一个端子上,得先拆开
  • 门磁是干接点还是带供电的?只有干接点能并接
  • 触点"闭合"对应门开还是门关?决定固件里的逻辑极性,反了改 inverted
  • 门框附近有没有空位放 ESP32 + 降压模块?门框上方的不锈钢箱子里通常有,但要量尺寸
  • 门禁断电时门是常开还是常闭?涉及消防和安防,改线前先跟物业和安全部门确认
  • 厂家质保和改造规定?有些门禁合同不允许第三方动线

B · 供电侧(必须实测)

  • 门禁 DC 输入是 12V 还是 24V?万用表直流档量,别看铭牌猜
  • 门磁两端子对控制器 GND 的电压?门关≈0V、门开≈12/24V → 控制器有上拉,必须光耦;两种状态都≈0V → 纯干接点
  • 这路是常电还是脉冲?优先取控制器 DC 输入或读卡器供电,别取电锁(部分门锁脉冲供电)
  • 带不带 UPS 后备?带最理想,停电时看板跟着门禁一起活
  • 降压模块先调到 5V 再接 ESP32MP1584EN 出厂默认输出 12V,直接接会烧
  • 降压模块能塞进盒子吗?带电位器的要留手拧的空间

C · 网络侧

  • 门边的 WiFi 信号够强吗?要站在门框位置看信号格,不要在办公室里测
  • ESP32 能不能访问到服务器?校园网开了 AP 隔离的话,手机能看看板 ≠ 传感器能连 broker
  • 服务器是固定内网 IP 吗?DHCP 一变,固件就找不到 broker 了 —— 建议在路由器上做静态绑定
  • 门禁后台有没有开放 API 或事件推送?有的话这条最省事,见降级路径

D · 下单前确认规格

  • 门磁:干接点、常开型确认接插件是 2 pin 还是螺丝端子
  • ESP32 开发板的尺寸要塞得进门边的盒子,Type-C 口更方便
  • 降压模块输入范围要覆盖 24VMP1584EN 上限 28V,够用
  • PC817 买 A 档CTR 更高,同样的电流亮度更足
  • 自购门磁时:门框材质 + 门缝宽度金属门影响吸合,缝隙以毫米计,买前问客服
  • 多扇门的话 deviceId 规划好接线和配置要一一对应

查出来不满足怎么办 —— 降级路径

每一行都是真实会卡住的地方。照着走,方案总能落下来,只是成本和复杂度不同。

备选方案 · 米家门磁 + 网关 + Home Assistant

最省事的一条兜底路:不动线、不借电、不烧固件,门磁贴上去、网关插上电就完事。 代价是多一层系统要维护 —— 但对"门框根本动不了"的场景,这是唯一能落地的方案。

图 5 · 米家方案链路。HA 处在"采集层",doorwatch 继续当"判定层 + 展示层"。 如果只给 IT 内部用,可以直接在 HA 这层收尾,不必接 doorwatch。
BLE 门磁只能走云端(米家云),延迟 30–60 秒 —— 这是 BLE 的固有限制,不是配置问题。

装之前必须先确认的两件事

① 门磁是蓝牙还是 Zigbee?

  • 小米门窗感应器 2(MCCGQ02HL)= 蓝牙 BLE,配蓝牙网关
  • 小米门窗感应器(一代)= Zigbee,配多模网关
  • Aqara 磁力门吸 E1/H1 = Zigbee,配多模网关

② 用哪个集成?

  • BLE 门磁 → 只能用 xiaomi_miot,官方集成看不到蓝牙设备
  • Zigbee 门磁 → 两个都行,优先小米官方 Xiaomi Home
  • 别两个都装,先试 xiaomi_miot,门磁没出现再换

依据:小米官网《Mi Door and Window Sensor 2 FAQ》与小米官方集成 ha_xiaomi_home 的说明文档。 完整接入步骤见项目里的 ha/README.md。

★ 传感器掉线时,看板怎么保证不撒谎

米家门磁这条路有个社区集成的坑:xiaomi_miot 在设备无响应时 不会把实体置为 unavailable,而是无限期保留最后一次读到的状态(issue #2699)。 所以「实体看起来还在」不等于「设备真的还活着」。 doorwatch 用三道防线挡住这件事 —— 任何一道生效,看板都只会显示「状态未知」。

  • 第一道 · 状态值模板在读不到传感器时输出 UNKNOWN;服务端认识这个值,收到就把状态打回「未知」并标记离线,而不是当成看不懂的值丢掉
  • 第二道 · 上报时间判传感器死活看的是「实体最后一次上报的时间」(last_reported),不是状态值本身 —— 值不变不代表设备还活着
  • 第三道 · 心跳心跳只证明「设备此刻还活着」,不证明「门是开是关」,所以它不会把已降级的状态复活;服务端自己的心跳超时负责兜底
  • 顺带挡掉broker 重放的 retained 旧消息只更新状态、不算存活 —— 否则服务端一重启,几天前的旧状态就会诈尸

还有一处容易漏:HA 的模板实体默认不会按时重算,所以自动化里每分钟用 homeassistant.update_entity 强制重算一次,新鲜度判据才拿得到「此刻」的时间。 实测降级耗时:收到 UNKNOWN 后 64 毫秒,收到 offline 后 3 毫秒 —— 不等 180 秒的心跳超时。

接进 doorwatch:两种配法,零代码改动

doorwatch 只认 MQTT 主题,所以谁当 broker 都行,二选一:

配法一 · HA 还没有 MQTT broker

让 HA 连 doorwatch 自带的 broker(1883,默认匿名),HA 往 doorwatch/it-office-door/state 发布。doorwatch 端什么都不用改。

配法二 · HA 已有 Mosquitto 集成

HA 只能有一个 MQTT broker 配置,那就反过来让 doorwatch 去连 HA 的 broker: 设 MQTT_HOST、MQTT_PORT_EXTERNAL、MQTT_USERNAME、 MQTT_PASSWORD。同样零代码改动,只改环境变量。

主题末尾的 it-office-door 必须和 config/doors.json 里的 deviceId 一致 —— 和 ESP32 方案是同一套规矩。

HA 侧需要的三个自动化

放进 HA 的 automations.yaml。关键点:心跳只在传感器可读时才发, 读不到就立刻推 status: offline 让看板降级成"未知",不等它自己超时。 

- alias: "门磁状态 → doorwatch"
  triggers:
    - trigger: state
      entity_id: sensor.doorwatch_it_office_door_state
  actions:
    - action: mqtt.publish
      data:
        topic: "doorwatch/it-office-door/state"
        payload: "{{ states('sensor.doorwatch_it_office_door_state') }}"
        qos: 1
        retain: true

- alias: "每分钟体检(★ 正确性的关键)"
  triggers:
    - trigger: time_pattern
      minutes: "/1"
  actions:
    # 模板默认不会按时重算,得强行刷一次
    - action: homeassistant.update_entity
      target:
        entity_id:
          - sensor.doorwatch_it_office_door_state
          - binary_sensor.doorwatch_it_office_door_readable
    - if:
        - condition: template
          value_template: >
            {% set r = states.binary_sensor.doorwatch_it_office_door_readable %}
            {% set ts = r.last_reported | default(r.last_updated, true) %}
            {% set ok = false %}
            {% if r is not none and r.state == 'on' and ts is defined and ts is not none %}
              {% set ok = (as_timestamp(now()) - as_timestamp(ts)) < 120 %}
            {% endif %}
            {{ ok }}
      then:
        - action: mqtt.publish
          data:
            topic: "doorwatch/it-office-door/state"
            payload: "{{ states('sensor.doorwatch_it_office_door_state') }}"
            qos: 1
            retain: true
        - action: mqtt.publish
          data:
            topic: "doorwatch/it-office-door/heartbeat"
            payload: "alive"
            qos: 1
      else:
        - action: mqtt.publish
          data:
            topic: "doorwatch/it-office-door/status"
            payload: "offline"
            qos: 1

- alias: "HA 启动时补发一次"
  triggers:
    - trigger: homeassistant
      event: start
  actions:
    - delay: "00:01:00"
    - action: homeassistant.update_entity
      target:
        entity_id:
          - sensor.doorwatch_it_office_door_state
          - binary_sensor.doorwatch_it_office_door_readable

落地要点(容易踩的坑)

  • 选对实体门磁会同时暴露 door(开合)和 motion(靠近)两个,要用 door 那个
  • BLE 门磁只能用 xiaomi_miot小米官方集成明确不支持蓝牙设备,用了看不到门磁
  • 方向可能反MIoT 的 contact-state 是「磁铁靠近=门关」,装完开一次门验证方向
  • 掉线不会变 unavailable集成会保留旧状态,必须靠上报时间判断死活,否则看板会撒谎
  • 用 last_reported 不用 last_updated状态和属性都没变时,HA 只推进 last_reported,last_updated 会冻住 —— 用错了会出现"传感器好好的,看板一直显示未知"
  • states('x') 只返回文本拿时间戳要写 states.x.last_reported,写错会每分钟抛模板错误
  • 模板不会按时重算值不变 = 不重算,新鲜度判据会卡住;每分钟 update_entity 强制重算一次
  • 失联要立刻推 offline别干等心跳超时 —— 实测 3ms 就能让看板降级
  • 门磁靠轮询,延迟 15–30 秒作者明确说门磁这类设备不适合做实时触发 —— 但「出门前扫一眼」够用
  • token 约 7 天会过期集成会集体失联,看板显示"状态未知"(安全,但要每周重载一次集成)

怎么选

你的情况选哪个
门框不能动线,也没有门禁可蹭方案三,这是唯一能落地的
学校已经有 Aqara 网关(智能灯、传感器那些)方案三,边际成本只有一个门磁
学校已经在跑 Home Assistant方案三,顺手把门磁接进 HA
只想给 IT 内部几个人看,不上全校方案三 + HA 卡片,连 doorwatch 都不用装
门框能拉线、有门禁可蹭电方案一,￥32 最便宜,而且完全自控
要完全掌控、离线可用、不依赖米家云方案一 / 二,ESP32 全程不出内网
要统一状态口径、要有历史记录、要给全校用方案一/二 接 doorwatch;方案三也接(HA 发 MQTT 即可)
三条路殊途同归。 无论传感器是 ESP32、门禁系统还是米家门磁,doorwatch 收到的都是同一组 MQTT 主题。 判定逻辑、看板、历史、告警,一份代码通吃 —— 换传感器只改采集端,不动服务端。 这也是为什么这个项目的服务端不掺任何硬件假设。

设备还在路上,现在就能做完的事

硬件到位后只剩两件事:改一个实体名、把方向开关拨对。其余现在就能做完。

  • 装 HA + xiaomi_miot先登录小米账号,把集成装好,设备到家直接绑定
  • 别绕 HACS只要这一个集成,一条 wget … install.sh 就行 —— 省掉绑 GitHub 账号和以后管更新的麻烦
  • 先跑一遍模拟node tools/demo.mjs --mode ha —— 不用硬件就能验证整条链路
  • 把自动化装好ha/templates.yaml + ha/automations.yaml 拷进 HA
  • 两边 broker 对上HA 的 MQTT 集成指向 doorwatch 的 1883,或者反过来设 MQTT_HOST
  • 确认 deviceId 一致doors.json 和自动化主题末段必须一样,否则服务端会打"未登记设备"告警
  • 规划摆放网关离门 5 米内最佳;门磁与磁铁间隙 < 18mm

--mode ha 模拟的是 HA 自动化的真实行为:状态变化才发消息,传感器读不到就不发心跳。 所以硬件没到,就能验证"传感器掉线 → 看板显示状态未知"这条最关键的路径。
